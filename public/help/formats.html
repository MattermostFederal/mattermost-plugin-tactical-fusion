Recognized Formats

What gets linked, what does not, and why the "does not" list is as long as it is.

Every format below can be switched off individually in the System Console. See Admin Settings. To see the current behavior of your own server rather than this page, run /tactical-fusion example-details, which runs the real matcher and posts what it did.

The rule everything follows

A format is eligible only if it resolves to a single instant. The link bakes an instant into its query string and the panel counts down to it, so anything needing a timezone invented for it is out. That single rule explains most of the declined list.

Military date-time group

Setting: EnableDTGMilitary

FormExampleNotes
DDHHMM + zone + MMM + YY 091630ZAUG26 Any zone letter except I and J. Month abbreviation is case insensitive.
DDHHMM + zone + MMM + YYYY 091630ZAUG2026 Same, with a four digit year.
DDHHMM + Z 091630Z Short form. Literal Z only. Month and year are taken from the date the message was posted, and the panel says so.

The year is restricted to 2000 to 2099, which is exactly the range two year digits can name without ambiguity.

091630R is not a date-time group here. The short form accepts only Z, because a bare six digits followed by a single letter is far too easy to hit by accident. Write 091630RAUG26 if you mean Romeo.

Labeled date-time group

Setting: EnableDTGMoniker

Some military formats mark where a time starts with a DTG: label. The label is matched and then dropped, so only the token itself becomes the link text:

You typeThe link text is
DTG: 091630ZAUG26091630ZAUG26
dtg:091630ZAUG26091630ZAUG26
DTG : 091630ZAUG26091630ZAUG26

Spacing either side of the colon is optional and the label is case insensitive. The token keeps its own casing rules.

The label vouches for nothing.

A token it marks still has to be a real one. DTG: 091630R is declined exactly as 091630R is. The label also only applies to formats that are themselves switched on, so turning military formats off also stops DTG: 091630ZAUG26.

RFC 3339 timestamp

Setting: EnableDTGTimestamp

The extended form only, with the hyphens and colons present:

ExampleNotes
2026-08-09T16:30:00ZUTC.
2026-08-09T20:30:00+04:00Any offset up to ±14:00, including half and quarter hour ones.
2026-08-09T16:30ZSeconds are optional.
2026-08-09T16:30:00.250ZFractional seconds are parsed and then discarded.
2026-08-09t16:30:00zLowercase t and z are accepted.

Military groups and RFC 3339 timestamps share one decorator because once parsed they are the same thing: an instant, plus the offset it was written in. They differ only in how that offset is carried, since an offset of +05:45 has no military letter to name it.

Deliberately declined

These look like times and are not matched. Each one is absent for a reason, and the reason is usually that a false positive here would corrupt somebody's message, since decoration rewrites what they wrote.

Not matchedExampleWhy
Epoch seconds 1786293000 Any ten digit number would qualify. Order numbers, ticket ids and phone numbers would all become links.
12 hour clocks 4:30 PM No date and no zone, so it names no instant. It would also match inside ordinary prose constantly.
Named zone abbreviations 16:30 CST CST is three different zones. EST collides with the abbreviation for "estimated".
Basic ISO 8601 20260809T163000Z With no hyphens there is no word boundary, so it would match inside snapshot-20260809T163000Z.zip.
Out of range offsets 2026-08-09T16:30:00+15:00 No inhabited zone is further than 14 hours from UTC, so a larger offset is a crafted value rather than a place. RFC 3339 permits up to ±23:59.
Dates outside 1970 to 2200 1918-11-11T11:00:00Z The panel and the standalone page only render an instant inside that window, so a timestamp outside it would become a link that does not open. Declining it leaves the text as written instead.
Bare dates 2026-08-09 Names a day, not an instant. Which midnight, in which zone?
Zoneless times 2026-08-09T16:30 Same problem. A zone would have to be invented for it.

Coordinates

Every coordinate grammar below normalizes to one latitude and longitude, so the panel reads the same whichever notation the author typed. Positions are WGS 84, always. A coordinate carrying another datum is declined rather than reinterpreted: NAD 27 and WGS 84 disagree by up to about 200 m in the continental United States, which is several grid cells.

Values are shown at the resolution the original text carried and no finer. A coordinate written to two decimals renders as 21.34° N, and a degrees-only coordinate renders degrees only. Padding a field the author never wrote would be a claim about precision they did not make.

Decimal degrees

WrittenAccepted
21.3353, -157.9483Signed. Needs a comma and at least four decimals on both values.
21.3353 N, 157.9483 WHemisphere letters. A decimal point is still required on both.
21.3353°N 157.9483°WDegree symbols optional.
N21.3353 W157.9483Letters may lead instead of trail.

The four-decimal rule on the signed form is what separates a coordinate from an ordinary pair of numbers, and it is the reason 21.34, -157.95 is left alone. Four decimals is about 11 m, which is what every real coordinate source emits; version pairs, ratios and tolerances essentially never carry it.

Degrees, minutes and seconds

WrittenAccepted
21°20'07"N 157°56'53"WSymbols, with or without spaces.
21° 20' 07" N, 157° 56' 53" WSpacing and the comma are both optional.
21 20 07 N 157 56 53 WSpaces instead of symbols.
21°20.118'N 157°56.898'WDegrees and decimal minutes, with no seconds.

Hemisphere letters are required in every variant. Without them the symbol-less form is six bare integers. Typographic variants are accepted, so a phone that turns an apostrophe into ’ or a quote into ” still produces a recognized coordinate.

USMTF compact shapes

The fixed-width forms used in ATO and USMTF 2004 traffic. An operator working from those messages pastes them unchanged, so they are recognized as written.

USMTF nameExampleResolution
LATD21N157WAbout 111 km. Label required.
LATM2120N15757WAbout 1.9 km
LATS212007N1575654WAbout 31 m
LATDS, DMPID212007.1N1575653.9WSub-meter
GEOK3510.234N07901.123WDegrees and thousandths of a minute
Verified2120N9-15757W7As LATM, plus a stated confidence digit per axis

The verified forms carry a confidence digit after each hemisphere letter. Those digits say how well the position is known, not where it is, so they are kept out of the coordinate and shown beside the resolution instead of being discarded.

Military grid references and UTM

These two are unlike everything above them: their position is calculated rather than read out of the text. Every other grammar here is arithmetic on digits the author typed, while a grid reference is a projection onto the WGS 84 ellipsoid, so it is worth knowing that the latitude and longitude shown for one is derived rather than quoted.

UTM is off by default. MGRS is on.

UTM is the only format in this plugin that ships disabled, because its band letter is ambiguous in a way MGRS's is not: the rows below marked UTM are matched only once an admin has turned EnableLocationUTM on. This does not affect the UTM row in the panel, which is shown for every decorated coordinate either way.

WrittenAccepted
4Q FJ 09060 59620Yes. A 1 m square
55P BR 76 02Yes. A 1 km square
4QFJ 09060 59620Yes. The digraph may run into the zone
4Q 609060 2359620Yes. UTM zone, band, easting, northing
4QFJ0906059620Yes. Run together, in upper case
4qfj0906059620No. Lower case is hash-shaped. Space it or label it
4QFJ090596Yes. Three digits per axis is the floor
4QFJ0959No. Coarser than 100 m. Space it or label it
MGRS:4qfj09Yes. A label reaches both
11S 385000 3769000Yes. S is a latitude band, not a hemisphere
55P 276020E 1502660NYes. The axis letters are optional
11N 385000 3769000No. That northing is not in band N
4QJJ123123No. J is not a 100 km letter in zone 4

A grid reference names a square, not a point.

55P BR 76 02 is a 1 km square, and the position shown for it is that square's center. Read as a corner instead, a 10 km reference would put a reader 7 km from where the grid points.

A run-together grid reference is matched on its own, with two restrictions that were chosen by measurement rather than by argument. It has to be upper case, because a short git commit hash is seven to twelve lower-case hexadecimal characters and that is exactly this shape: about one in 3,900 of them is a well-formed grid reference. And it needs at least three digits per axis, a 100 m square, because a shorter run is what a part number looks like: at two digits per axis 26HMA1997 and 3UTA7623 are valid grid references, about one in 75,000 uppercase runs. At three, a sweep of 1.2 million finds none. This is the same rule that keeps 21N157W behind a label. Neither restriction puts anything out of reach: space it, or write MGRS:, UTMO: or UTMT: in front, and both work.

UTM run together is matched only behind a label, and that is not an oversight. After the zone and band it is thirteen bare digits with no letters to check, so the only validation available is that the northing lands in the band, which a great many thirteen-digit runs do. There is nothing there to make narrower.

The letter after a UTM zone is a latitude band. 11S 385000 3769000 is band S, so it resolves to 34 north. It is not read as "zone 11, southern hemisphere", which would put it at 56 south. Nothing in the token says which was meant, so this is a convention: MGRS is the military implementation of UTM, and the third character of a grid zone designator is a latitude band.

The two letters do not carry the same risk. For N, both readings put the point in the same place, and reading it as a band only adds the requirement that the position be in the first 8 degrees north; it can decline a coordinate but never move one. S is where the difference is real, and what limits it is that the northing has to land inside the band its letter names. About 90% of positions written in the hemisphere convention fail that check and are declined rather than relocated.

The axis letters are optional. 55P 276020E 1502660N and 55P 276020mE 1502660mN are both matched, and mean exactly what the same pair without them means. They must be attached to their digits: a space before one would let the token swallow the first letter of the following word.

The 100 km letters are checked against the zone. Only eight of the twenty-four possible column letters are legal in any given zone, and the row letters are staggered in even-numbered zones, so a reference whose letters name no real square is declined rather than resolved to whatever the arithmetic produces.

Above 84° north and below 80° south there is no UTM grid: that is the Universal Polar Stereographic system, which this plugin does not implement. A polar coordinate is still decorated and still shows latitude and longitude, it simply has no grid rows.

Area references: GEOREF, GARS and Plus Codes

Three notations that name a cell of the graticule rather than a point, the way a grid reference names a square. They need no projection, which has one visible consequence: they still render above 84° north and below 80° south, where the MGRS and UTM rows are blank.

NotationExampleCell
GEOREFGEOREF:XGKP55351 minute
GEOREFGEOREF:XGKP553350a tenth of a minute
GEOREFGEOREF:XGKP55803503a hundredth
GARSGARS:045KG30 minutes
GARSGARS:045KG115 minutes
GARSGARS:045KG145 minutes
Plus Code73H483P2+4Mabout 14 m
Plus Code73H483P2+4MGabout 3 m
Plus Code73H40000+1 degree, padded

GEOREF is written longitude first. That is the standard's own order and the opposite of every other format on this page: in XGKP5535, X, K and 55 are longitude and G, P and 35 are latitude.

GEOREF and GARS are matched behind their labels and never bare. XGKP5535 is four letters and four digits, and 045KG14 is seven alphanumerics whose only structural check rules out just over a third of the possible letter pairs. Neither has anything in it a part number does not, so a bare pattern would rewrite ordinary text. This is the same posture LATD is held to.

A Plus Code is matched without a label, in upper case. Its twenty-character alphabet contains no vowel at all, so an eight-character run of it is not a word, and the separator sits at a fixed position in the middle. Lower case needs a PLUSCODE: or OLC: label, because a lower-case run of that shape is what a version string with build metadata looks like and about one in 50,000 of those is a well-formed code.

Short Plus Codes such as CWC8+R9 are left alone. They are meaningless without a nearby reference location, which this plugin does not have.

Labeled coordinates

A field label in front of any enabled grammar is recognized: LATD:, LATM:, LATS:, LATDS:, GEOK:, DMPID:, DEPLATM:, ARRLATM:, the verified variants VLATD:, VLATM:, VLATS: and VGEOT:, the grid labels MGRS:, USNG:, UTMO:, UTMT:, DEPUTMO: and ARRUTMO:, and the area-reference labels GEOREF:, GARS:, PLUSCODE: and OLC:.

USNG: introduces a grid reference. The United States National Grid is MGRS on WGS 84, character for character, so it is not a separate format here: a USNG: token is read and stored as MGRS.

Like the DTG: label, a coordinate label is consumed: the label and the token together become the link, so LATM:2120N15757W is stored as a link reading 2120N15757W. The label said what kind of thing followed, and once the thing is a link that says so itself the label is repeating it:

A label is guarded on both sides exactly as a bare coordinate is, so MGRS:4QFJ0906059620 inside a path such as logs/MGRS:4QFJ0906059620 is left alone. That means a USMTF line quoted with slash delimiters does not decorate; a genuine one ends // and is left alone for the same reason. That is also what bounds the cost of consuming the label: the lines most likely to be quoted verbatim as a structured record are exactly the ones that never decorate. 

LATM:2130N15730W

becomes a link on the coordinate alone, with LATM: still in front of it.

A label vouches for nothing. LATM:9999N99999W stays declined, exactly as 9999N99999W does.

Labels are the only way to reach the shortest shape.

21N157W is seven characters, two of them letters, and it resolves to a 111 km square. It is available behind a label and nowhere else. Turning every grammar off except the USMTF one and the label leaves a configuration that decorates only what an author explicitly marked, which is a supported way to run this.

Coordinates deliberately declined

The same principle as the times above: a false positive here rewrites somebody's message permanently, so anything that could plausibly be ordinary text is left alone.

Not matchedExampleWhy
Coarse decimal pairs 21.34, -157.95 Fewer than four decimals. Two short decimals and a comma appear constantly in ordinary text.
Integer pairs 12, 34 Scores, counts, ranges, anything.
No delimiter 21.3353 -157.9483 A space between two numbers is not evidence that they are a pair.
Units that look like hemispheres Load 12 N, 5 W N, S, E and W are also newton, siemens, east and watt. The decimal-point requirement is what keeps this out.
Part of a numeric list 0.1234, 0.5678, 0.9012 A coordinate next to another number is a list, not a position.
Inside a longer run -157.9483..-157.9583 A range. Linking the middle of one would break it.
Comma as a decimal separator 21,3353, -157,9483 Ambiguous with the separator between the pair. Declined rather than guessed at.
Out of range 9999N99999W Latitude past 90 or longitude past 180 is not a place.
Bare LATD 21N157W Too short to detect on its own. LATD:21N157W is recognized.
Bare GEOREF XGKP5535 Four letters and four digits is also a part number. GEOREF:XGKP5535 is recognized.
Bare GARS 045KG14 Seven alphanumerics with almost nothing in them to check. GARS:045KG14 is recognized.
Lower-case Plus Code 73h483p2+4m That shape is what a version string with build metadata looks like, and about one in 50,000 of those is a valid code. PLUSCODE:73h483p2+4m is recognized.
Short Plus Code CWC8+R9 Meaningless without a nearby reference location, which this plugin does not have and would have to guess at.
Null Island 0.0000, 0.0000 Overwhelmingly an unset field rather than a position in the Gulf of Guinea. A single zero component beside a real value is accepted.
Another datum 21.3353, -157.9483 NAD27 Resolves to a different place. Declined rather than silently treated as WGS 84.
Run-together grid references in lower case, or coarser than 100 m 4qfj0906059620, 4QFJ0959 A lower-case run of that shape is what a short git commit hash looks like, and a shorter one is what a part number looks like. Upper case with three digits per axis is matched, so 4QFJ0906059620 is a link; space these out or put MGRS: in front to reach the rest.
A UTM northing outside its band 11N 385000 3769000 The letter after the zone is a latitude band, and that northing is 34 north, which is band S. Note this also means 11S is not read as "zone 11, southern hemisphere".
Grid squares that do not exist 4QJJ123123 Only eight of the twenty-four column letters are legal in any zone, and D is not one of zone 32's.
Polar grid references ZAH 12345 67890 Universal Polar Stereographic, above 84° north or below 80° south. A different system, not implemented.
Airfield codes ICAO:KJFK Names a facility whose position has to be looked up rather than computed, so it is not read as a coordinate. It is recognized by the airfield decorator instead, which looks it up.
Bearing and range BAR:330-PT ALFA-50 Relative to a reference point that is not in the message, so there is nothing to resolve it against.

Not sure why yours was not linked?

/tactical-fusion check <your text> runs the real matcher against it and tells you, without posting anything.

Airfield codes

An ICAO airfield code is four letters naming a facility, so unlike every coordinate on this page its position is looked up rather than computed. The plugin carries an airfield database and resolves the code against it, then derives every coordinate reading from the position it finds.

What is recognizedExampleNotes
Behind a USMTF field label ICAO:PHNL The four labels that introduce an airfield code in USMTF: ICAO:, LOC:, DEPLOC: and ARRLOC:.
A space before the colon ICAO :PHNL Spaces and tabs before the colon are optional. Nothing may follow it: see the declined list. A line break is not allowed either, so a label at the end of a line never claims the next line's first word.
Ending a USMTF set line DEPLOC:PHNL// The trailing // is left in the message and kept out of the link.

Airfield codes deliberately declined

What is not linkedExampleWhy
Anything after the colon LOC: FAST The code must be written directly against the colon, which a genuine USMTF field is. A space would let the label reach the next word of an ordinary sentence, and military traffic is often written in capitals: LOC: FAST TURNAROUND ON THE RAMP would otherwise rewrite FAST into a link to Somerset East Airport, permanently. Write LOC:FAST when you mean the airfield.
A code with no label KIND Four letters is what ordinary words are made of. 343 codes in the database are English dictionary words, including FACT (Cape Town International) and FAST (Somerset East), and USCG is an airfield in Russia. Linking bare codes would rewrite ordinary sentences into links pointing at the wrong side of the world.
A lower-case label icao:phnl Same reason. A line like loc: fast turnaround on the ramp would otherwise be rewritten. USMTF field labels are upper case.
A code the database does not hold ICAO:QZQZ The code is validated by looking it up, not by its shape, so four letters on their own vouch for nothing.
ZZZZ DEPLOC:ZZZZ In a flight plan this means "aerodrome not listed", with the real field named in remarks. It is a real airfield upstream, and linking it would name a specific island airfield where the message means "see remarks", so it is deliberately not in the database.
IATA codes IND Three letters, and not implemented in this version. The IATA code is shown in the panel for an airfield that has one.
A label inside a path logs/ICAO:PHNL A label with a path character in front of it is not a field label, and rewriting the middle of a path is exactly what the plugin's boundary rules exist to prevent.

The position is a reference point

The airfield database gives one position per field, quoted to four decimal places, which is about 11 metres. It is a reference point for the field rather than a surveyed location of the tower, the threshold or any particular part of it. Where the data comes from is recorded on this page and beside the data itself rather than in the panel, which prints no credit. The panel draws the position as a map and links to the coordinate panel for the readings rather than reprinting them.

Cursor on Target events

A Cursor on Target event is rendered as a card rather than linked: the callsign and what the event says it is, the position, when it was taken and when it goes stale, and how accurately the position is known. The position is drawn on a map with its stated circular error around it, so a three-metre fix and a nine-kilometre fix do not look alike.

There are two ways to post one.

In a fenced code block

Paste the event into a fenced block labelled cot or xml: 

```cot
<event version="2.0" uid="ANDROID-1" type="a-f-G-U-C" how="m-g"
       time="2026-08-23T11:43:38Z" stale="2026-08-23T11:45:38Z">
  <point lat="21.335300" lon="-157.948300" ce="45.3" le="99.5"/>
  <detail><contact callsign="DELTA1"/></detail>
</event>
```

Both labels are read the same way. Use cot when you mean it: a block labelled xml that turns out not to be an event is left alone silently, because plenty of XML is not Cursor on Target, while a block you labelled cot tells you why it was not rendered.

As an attached file

Attach exactly one file whose name ends .cot or .xml. The card names the file and links to it, so the original is always one click away. Files over 64 KB are left as ordinary attachments.

It has to be a file you attached to this post. A file already carried by another post, one somebody else uploaded, or one that has been deleted is left alone and the post goes out as ordinary text. The plugin reads the attachment before the server has finished binding it to the post, so this is the only thing standing between a quoted file id and that file's contents being copied into a post anyone in the channel can read.

What is and is not rendered

You can write a covering note around the event and it is kept. There are limits worth knowing before they surprise you:

  • Markdown in that note is not formatted. The plugin draws the whole post body itself and has no access to Mattermost's formatter, so bold, links and lists beside an event render as the characters you typed.
  • Several events in one block are read together. The card names each one and links its position, and the full detail of every event is behind Open details. Up to 32; a block carrying more is left alone rather than shown in part. If any single event in the block is malformed, none of them is rendered.
  • An event may name up to 16 others. Past that the extra link elements are dropped and the event still renders, which is deliberately the opposite of the 32 event limit above. Losing a relation costs one entry in a Relates to row that has already told you who sent the event; losing an event would leave a card quietly claiming a set it does not hold.
  • A fence is optional. An event pasted straight into a message is read the same way, with your surrounding text kept. An event you put in a code block without labelling the fence is left as code, because that is what you said it was.
  • Two fenced blocks are left alone. Put the events in one block, or post them separately.
  • Two attachments means no card. The file has to be the only one.
  • Editing the post removes the card, permanently. The event was read once, when the post was created, and an edit can change the text it was read from. Rather than show you a card that might no longer match, the post falls back to its own text.
  • A coordinate written beside an event is not linked. The card owns the post body, so a link written into the text around it could not render. The position inside the event is linked by the card itself.
  • The post will not be found by search on installs that use Elasticsearch or OpenSearch. See the admin note.

An event must carry a uid, a type and a time to be rendered at all. Without those the card would be a table of blanks, which is worse than the XML it replaced.

What the card will not claim

  • An accuracy the event did not state is not invented. The row says so and no circle is drawn.
  • 9999999.0 is the Cursor on Target value for "not known". It is shown as not stated, never as a figure.
  • A position of 0,0 is shown, and named as the value an unset Cursor on Target point carries, but no pin is drawn for it.
  • A position written too coarsely to satisfy the coordinate grammar is shown as text without a link, rather than padded out with digits the event never had.
  • An event that names the unit which sent it shows that as Sent by, and any other events it names as Relates to. Nothing tries to find those other events; the codes are shown as the event wrote them.
  • An event type is decoded as far as this build knows it and no further, so a-f-G-U-C reads as Friendly Ground Combat Unit and a-f-A as Friendly Air. A code carrying more than the build recognizes keeps the deepest part it does know rather than guessing at the rest, and a type outside the recognized set says it is unrecognized. The raw code is always shown in brackets beside the label, so you can see what the label came from and what it did not cover.
  • Staleness is measured between two values fixed on the server, so it reads the same for everyone regardless of what any workstation clock says. The card is a snapshot of what was posted, not a live track, and nothing on it ticks.

Spans that are never rewritten

The matcher protects spans, not whole messages. A token in ordinary prose is still linked even when the message also contains a code block or a URL; a token inside one of those is left alone. So this: 

[the plan](https://example.com/brief) says 091630ZAUG26

links the date-time group and leaves the existing link untouched.

The protected constructs are:

  • Fenced code blocks, including unterminated ones and ~~~ fences
  • Indented code blocks
  • Inline code of any backtick width
  • Links, images, and reference definitions
  • Any bracketed span
  • Angle autolinks, such as <https://example.com>
  • Inline HTML tags
  • Bare URLs beginning scheme:// or www.

Decoration is also skipped entirely, leaving the message exactly as written, when the result would exceed the maximum post size. A twelve character date-time group becomes roughly a hundred and twenty once linked, so a message that visibly fits can cross the limit here. Posting it undecorated is better than showing the author an opaque "too long" error for text they can see fits.
