Recognized Formats

What gets linked, what does not, and why the "does not" list is as long as it is.

Every format below can be switched off individually in the System Console. See Admin Settings. To see the current behavior of your own server rather than this page, run /tactical-fusion example-details, which runs the real matcher and posts what it did.

The rule everything follows

A format is eligible only if it resolves to a single instant. The link bakes an instant into its query string and the panel counts down to it, so anything needing a timezone invented for it is out. That single rule explains most of the declined list.

Military date-time group

Setting: EnableDTGMilitary

FormExampleNotes
DDHHMM + zone + MMM + YY 091630ZAUG26 Any zone letter except I and J. Month abbreviation is case insensitive.
DDHHMM + zone + MMM + YYYY 091630ZAUG2026 Same, with a four digit year.
DDHHMM + Z 091630Z Short form. Literal Z only. Month and year are taken from the date the message was posted, and the panel says so.

The year is restricted to 2000 to 2099, which is exactly the range two year digits can name without ambiguity.

091630R is not a date-time group here. The short form accepts only Z, because a bare six digits followed by a single letter is far too easy to hit by accident. Write 091630RAUG26 if you mean Romeo.

Labeled date-time group

Setting: EnableDTGMoniker

Some military formats mark where a time starts with a DTG: label. The label is matched and then dropped, so only the token itself becomes the link text:

You typeThe link text is
DTG: 091630ZAUG26091630ZAUG26
dtg:091630ZAUG26091630ZAUG26
DTG : 091630ZAUG26091630ZAUG26

Spacing either side of the colon is optional and the label is case insensitive. The token keeps its own casing rules.

The label vouches for nothing.

A token it marks still has to be a real one. DTG: 091630R is declined exactly as 091630R is. The label also only applies to formats that are themselves switched on, so turning military formats off also stops DTG: 091630ZAUG26.

RFC 3339 timestamp

Setting: EnableDTGTimestamp

The extended form only, with the hyphens and colons present:

ExampleNotes
2026-08-09T16:30:00ZUTC.
2026-08-09T20:30:00+04:00Any offset up to ±14:00, including half and quarter hour ones.
2026-08-09T16:30ZSeconds are optional.
2026-08-09T16:30:00.250ZFractional seconds are parsed and then discarded.
2026-08-09t16:30:00zLowercase t and z are accepted.

Military groups and RFC 3339 timestamps share one decorator because once parsed they are the same thing: an instant, plus the offset it was written in. They differ only in how that offset is carried, since an offset of +05:45 has no military letter to name it.

Deliberately declined

These look like times and are not matched. Each one is absent for a reason, and the reason is usually that a false positive here would corrupt somebody's message, since decoration rewrites what they wrote.

Not matchedExampleWhy
Epoch seconds 1786293000 Any ten digit number would qualify. Order numbers, ticket ids and phone numbers would all become links.
12 hour clocks 4:30 PM No date and no zone, so it names no instant. It would also match inside ordinary prose constantly.
Named zone abbreviations 16:30 CST CST is three different zones. EST collides with the abbreviation for "estimated".
Basic ISO 8601 20260809T163000Z With no hyphens there is no word boundary, so it would match inside snapshot-20260809T163000Z.zip.
Out of range offsets 2026-08-09T16:30:00+15:00 No inhabited zone is further than 14 hours from UTC, so a larger offset is a crafted value rather than a place. RFC 3339 permits up to ±23:59.
Dates outside 1970 to 2200 1918-11-11T11:00:00Z The panel and the standalone page only render an instant inside that window, so a timestamp outside it would become a link that does not open. Declining it leaves the text as written instead.
Bare dates 2026-08-09 Names a day, not an instant. Which midnight, in which zone?
Zoneless times 2026-08-09T16:30 Same problem. A zone would have to be invented for it.

Coordinates

Every coordinate grammar below normalizes to one latitude and longitude, so the panel reads the same whichever notation the author typed. Positions are WGS 84, always. A coordinate carrying another datum is declined rather than reinterpreted: NAD 27 and WGS 84 disagree by up to about 200 m in the continental United States, which is several grid cells.

Values are shown at the resolution the original text carried and no finer. A coordinate written to two decimals renders as 34.06° N, and a degrees-only coordinate renders degrees only. Padding a field the author never wrote would be a claim about precision they did not make.

Decimal degrees

WrittenAccepted
34.0561, -118.2500Signed. Needs a comma and at least four decimals on both values.
34.0561 N, 118.2500 WHemisphere letters. A decimal point is still required on both.
34.0561°N 118.2500°WDegree symbols optional.
N34.0561 W118.2500Letters may lead instead of trail.

The four-decimal rule on the signed form is what separates a coordinate from an ordinary pair of numbers, and it is the reason 34.05, -118.25 is left alone. Four decimals is about 11 m, which is what every real coordinate source emits; version pairs, ratios and tolerances essentially never carry it.

Degrees, minutes and seconds

WrittenAccepted
34°03'22"N 118°15'00"WSymbols, with or without spaces.
34° 03' 22" N, 118° 15' 00" WSpacing and the comma are both optional.
34 03 22 N 118 15 00 WSpaces instead of symbols.
34°03.366'N 118°15.000'WDegrees and decimal minutes, with no seconds.

Hemisphere letters are required in every variant. Without them the symbol-less form is six bare integers. Typographic variants are accepted, so a phone that turns an apostrophe into ’ or a quote into ” still produces a recognized coordinate.

USMTF compact shapes

The fixed-width forms used in ATO and USMTF 2004 traffic. An operator working from those messages pastes them unchanged, so they are recognized as written.

USMTF nameExampleResolution

LATM3510N07901WAbout 1.9 km

The verified forms carry a confidence digit after each hemisphere letter. Those digits say how well the position is known, not where it is, so they are kept out of the coordinate and shown beside the resolution instead of being discarded.

Military grid references and UTM

These two are unlike everything above them: their position is calculated rather than read out of the text. Every other grammar here is arithmetic on digits the author typed, while a grid reference is a projection onto the WGS 84 ellipsoid, so it is worth knowing that the latitude and longitude shown for one is derived rather than quoted.

UTM is off by default. MGRS is on.

UTM is the only format in this plugin that ships disabled, because its band letter is ambiguous in a way MGRS's is not: the rows below marked UTM are matched only once an admin has turned EnableLocationUTM on. This does not affect the UTM row in the panel, which is shown for every decorated coordinate either way.

WrittenAccepted

33U 291000 5628000Yes. UTM zone, band, easting, northing

18suj2347806483No. Lower case is hash-shaped. Space it or label it
18SUJ234064Yes. Three digits per axis is the floor
18SUJ2306No. Coarser than 100 m. Space it or label it
MGRS:18suj23Yes. A label reaches both
11S 385000 3769000Yes. S is a latitude band, not a hemisphere
11S 384640E 3769080NYes. The axis letters are optional
11N 385000 3769000No. That northing is not in band N
32WDL123123No. D is not a 100 km letter in zone 32

A grid reference names a square, not a point.

32U MV 12 34 is a 1 km square, and the position shown for it is that square's center. Read as a corner instead, a 10 km reference would put a reader 7 km from where the grid points.

A run-together grid reference is matched on its own, with two restrictions that were chosen by measurement rather than by argument. It has to be upper case, because a short git commit hash is seven to twelve lower-case hexadecimal characters and that is exactly this shape: about one in 3,900 of them is a well-formed grid reference. And it needs at least three digits per axis, a 100 m square, because a shorter run is what a part number looks like: at two digits per axis 26HMA1997 and 3UTA7623 are valid grid references, about one in 75,000 uppercase runs. At three, a sweep of 1.2 million finds none. This is the same rule that keeps 35N079W behind a label. Neither restriction puts anything out of reach: space it, or write MGRS:, UTMO: or UTMT: in front, and both work.

UTM run together is matched only behind a label, and that is not an oversight. After the zone and band it is thirteen bare digits with no letters to check, so the only validation available is that the northing lands in the band, which a great many thirteen-digit runs do. There is nothing there to make narrower.

The letter after a UTM zone is a latitude band. 11S 385000 3769000 is band S, so it resolves to 34 north. It is not read as "zone 11, southern hemisphere", which would put it at 56 south. Nothing in the token says which was meant, so this is a convention: MGRS is the military implementation of UTM, and the third character of a grid zone designator is a latitude band.

The two letters do not carry the same risk. For N, both readings put the point in the same place, and reading it as a band only adds the requirement that the position be in the first 8 degrees north; it can decline a coordinate but never move one. S is where the difference is real, and what limits it is that the northing has to land inside the band its letter names. About 90% of positions written in the hemisphere convention fail that check and are declined rather than relocated.

The axis letters are optional. 11S 384640E 3769080N and 11S 384640mE 3769080mN are both matched, and mean exactly what the same pair without them means. They must be attached to their digits: a space before one would let the token swallow the first letter of the following word.

The 100 km letters are checked against the zone. Only eight of the twenty-four possible column letters are legal in any given zone, and the row letters are staggered in even-numbered zones, so a reference whose letters name no real square is declined rather than resolved to whatever the arithmetic produces.

Above 84° north and below 80° south there is no UTM grid: that is the Universal Polar Stereographic system, which this plugin does not implement. A polar coordinate is still decorated and still shows latitude and longitude, it simply has no grid rows.

Area references: GEOREF, GARS and Plus Codes

Three notations that name a cell of the graticule rather than a point, the way a grid reference names a square. They need no projection, which has one visible consequence: they still render above 84° north and below 80° south, where the MGRS and UTM rows are blank.

NotationExampleCell
GEOREFGEOREF:GJNJ57531 minute
GEOREFGEOREF:GJNJ575337a tenth of a minute
GEOREFGEOREF:GJNJ57533752a hundredth
GARSGARS:206LT30 minutes

GARSGARS:006AG395 minutes
Plus Code849VCWC8+R9about 14 m
Plus Code849VCWC8+R9Cabout 3 m
Plus Code849V0000+1 degree, padded

GEOREF is written longitude first. That is the standard's own order and the opposite of every other format on this page: in GJNJ5753, G, N and 57 are longitude and J, J and 53 are latitude.

GEOREF and GARS are matched behind their labels and never bare. GJNJ5753 is four letters and four digits, and 006AG39 is seven alphanumerics whose only structural check rules out two thirds of the possible letter pairs. Neither has anything in it a part number does not, so a bare pattern would rewrite ordinary text. This is the same posture LATD is held to.

A Plus Code is matched without a label, in upper case. Its twenty-character alphabet contains no vowel at all, so an eight-character run of it is not a word, and the separator sits at a fixed position in the middle. Lower case needs a PLUSCODE: or OLC: label, because a lower-case run of that shape is what a version string with build metadata looks like and about one in 50,000 of those is a well-formed code.

Short Plus Codes such as CWC8+R9 are left alone. They are meaningless without a nearby reference location, which this plugin does not have.

Labeled coordinates

A field label in front of any enabled grammar is recognized: LATD:, LATM:, LATS:, LATDS:, GEOK:, DMPID:, DEPLATM:, ARRLATM:, the verified variants VLATD:, VLATM:, VLATS: and VGEOT:, the grid labels MGRS:, USNG:, UTMO:, UTMT:, DEPUTMO: and ARRUTMO:, and the area-reference labels GEOREF:, GARS:, PLUSCODE: and OLC:.

USNG: introduces a grid reference. The United States National Grid is MGRS on WGS 84, character for character, so it is not a separate format here: a USNG: token is read and stored as MGRS.

Unlike the DTG: label, a coordinate label is kept in the message rather than consumed. It is part of a structured line the author may be quoting verbatim, so a decorated USMTF line still reads as USMTF:

A label is guarded on both sides exactly as a bare coordinate is, so MGRS:18SUJ2347806483 inside a path such as logs/MGRS:18SUJ2347806483 is left alone. That means a USMTF line quoted with slash delimiters does not decorate; a genuine one ends // and was already left alone for the same reason. 

LATM:2130N15730W

becomes a link on the coordinate alone, with LATM: still in front of it.

A label vouches for nothing. LATM:9999N99999W stays declined, exactly as 9999N99999W does.

Labels are the only way to reach the shortest shape.

35N079W is seven characters, two of them letters, and it resolves to a 111 km square. It is available behind a label and nowhere else. Turning every grammar off except the USMTF one and the label leaves a configuration that decorates only what an author explicitly marked, which is a supported way to run this.

Coordinates deliberately declined

The same principle as the times above: a false positive here rewrites somebody's message permanently, so anything that could plausibly be ordinary text is left alone.

Not matchedExampleWhy
Coarse decimal pairs 34.05, -118.25 Fewer than four decimals. Two short decimals and a comma appear constantly in ordinary text.
Integer pairs 12, 34 Scores, counts, ranges, anything.
No delimiter 34.0561 -118.2500 A space between two numbers is not evidence that they are a pair.
Units that look like hemispheres Load 12 N, 5 W N, S, E and W are also newton, siemens, east and watt. The decimal-point requirement is what keeps this out.
Part of a numeric list 0.1234, 0.5678, 0.9012 A coordinate next to another number is a list, not a position.
Inside a longer run -118.2500..-118.2600 A range. Linking the middle of one would break it.
Comma as a decimal separator 34,0561, -118,2500 Ambiguous with the separator between the pair. Declined rather than guessed at.
Out of range 9999N99999W Latitude past 90 or longitude past 180 is not a place.
Bare LATD 35N079W Too short to detect on its own. LATD:35N079W is recognized.
Bare GEOREF GJNJ5753 Four letters and four digits is also a part number. GEOREF:GJNJ5753 is recognized.
Bare GARS 006AG39 Seven alphanumerics with almost nothing in them to check. GARS:006AG39 is recognized.
Lower-case Plus Code 849vcwc8+r9 That shape is what a version string with build metadata looks like, and about one in 50,000 of those is a valid code. PLUSCODE:849vcwc8+r9 is recognized.
Short Plus Code CWC8+R9 Meaningless without a nearby reference location, which this plugin does not have and would have to guess at.
Null Island 0.0000, 0.0000 Overwhelmingly an unset field rather than a position in the Gulf of Guinea. A single zero component beside a real value is accepted.
Another datum 34.0561, -118.2500 NAD27 Resolves to a different place. Declined rather than silently treated as WGS 84.
Run-together grid references in lower case, or coarser than 100 m 18suj2347806483, 18SUJ2306 A lower-case run of that shape is what a short git commit hash looks like, and a shorter one is what a part number looks like. Upper case with three digits per axis is matched, so 18SUJ2347806483 is a link; space these out or put MGRS: in front to reach the rest.
A UTM northing outside its band 11N 385000 3769000 The letter after the zone is a latitude band, and that northing is 34 north, which is band S. Note this also means 11S is not read as "zone 11, southern hemisphere".
Grid squares that do not exist 32WDL123123 Only eight of the twenty-four column letters are legal in any zone, and D is not one of zone 32's.
Polar grid references ZAH 12345 67890 Universal Polar Stereographic, above 84° north or below 80° south. A different system, not implemented.
GARS, GEOREF, Plus Codes 006AG39, 849VCWC8+R9 Not implemented in this version.
Airfield codes ICAO:KJFK Names a facility whose position has to be looked up rather than computed, so it is not a coordinate. Out of scope for this decorator.
Bearing and range BAR:330-PT ALFA-50 Relative to a reference point that is not in the message, so there is nothing to resolve it against.

Not sure why yours was not linked?

/tactical-fusion check <your text> runs the real matcher against it and tells you, without posting anything.

Spans that are never rewritten

The matcher protects spans, not whole messages. A token in ordinary prose is still linked even when the message also contains a code block or a URL; a token inside one of those is left alone. So this: 

[the plan](https://example.com/brief) says 091630ZAUG26

links the date-time group and leaves the existing link untouched.

The protected constructs are:

  • Fenced code blocks, including unterminated ones and ~~~ fences
  • Indented code blocks
  • Inline code of any backtick width
  • Links, images, and reference definitions
  • Any bracketed span
  • Angle autolinks, such as <https://example.com>
  • Inline HTML tags
  • Bare URLs beginning scheme:// or www.

Decoration is also skipped entirely, leaving the message exactly as written, when the result would exceed the maximum post size. A twelve character date-time group becomes roughly a hundred and twenty once linked, so a message that visibly fits can cross the limit here. Posting it undecorated is better than showing the author an opaque "too long" error for text they can see fits.
