GeoJSON

The overlay format every GIS tool speaks, rendered as a card with its features drawn on a map.

Settings: EnableGeoJSON and EnableGeoJSONFile. The example on this page is the one this build's own /tactical-fusion examples posts, so what you read here is what your server will do.

A GeoJSON document is rendered as a card rather than linked: how many features the document holds and of what geometry, each one named, the properties it carries, and every feature drawn together on one map fitted to all of them. A polygon's holes are drawn as holes, and two lines that do not touch are drawn as two lines.

Posting a document

In a fenced code block

Paste the document into a fence labeled geojson:

```geojson
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {"type": "Point", "coordinates": [-157.9483, 21.3353]},
      "properties": {"name": "Forward supply point", "status": "active"}
    },
    {
      "type": "Feature",
      "geometry": {"type": "LineString", "coordinates": [
        [-157.9483, 21.3353], [-157.9300, 21.3400]
      ]},
      "properties": {"name": "Primary route"}
    }
  ]
}
```

A fence labeled json is not read unless an admin asks for it.

Rendering a post this way sets its type, and a typed post loses its Elasticsearch and OpenSearch matches permanently. Ordinary JSON is pasted into chat constantly, and an author who got one rendered by mistake has no way to undo it. So geojson is the only spelling read out of the box. An install that wants the others can turn on EnableGeoJSONUnlabeled; see below.

As an attachment

A post carrying exactly one attachment whose name ends .geojson is read as the post is created, and the card replaces the attachment rather than sitting beside it. Files over 64 KB are ignored, and a .json attachment is never read for the reason above.

This is the only other setting in the plugin that reads a file while a message is being posted. An install whose file storage is slow or remote may prefer EnableGeoJSONFile off and the fenced block instead, which costs nothing extra.

What this build reads

Every geometry RFC 7946 defines, wherever it appears: on its own, inside a Feature, or inside a FeatureCollection.

TypeDrawn as
Point, MultiPointA marker per position.
LineString, MultiLineStringA line per part. Two disjoint lines stay two lines.
Polygon, MultiPolygonAn area. The first ring is the outside and the rest are holes.
GeometryCollection, one level deepEach member in whichever way its own type is drawn, so one feature can be both markers and shapes.
"geometry": nullListed with a note. RFC 7946 allows a feature with no position, and it is not an error.

Coordinates are read longitude first, which is what RFC 7946 specifies and what every conforming tool writes. Each one is shown with the digits the document wrote: a coordinate written 1e-05 or to sixteen decimal places is read and drawn, because that is ordinary output from ogr2ogr and from Python's json module.

What this build refuses

A document past any of these is left as an ordinary code block, and an author who wrote an explicit geojson fence is told why. Nothing is truncated: a card showing the first 256 features of nine hundred would be quietly wrong about what was posted.

LimitValue
Document size64 KB
Features256
Coordinates, across the whole document4096
Properties per feature32, with values shortened past 256 characters
Nesting32 levels, and a GeometryCollection may not contain another

At the precision a real export writes, the 64 KB limit is reached at roughly 2,500 coordinates, so it is usually the one you meet first. Attaching the file does not raise it: an attachment over 64 KB is ignored the same way. Split the overlay instead, or simplify its geometry.

What is listed but not drawn

These do not refuse the document. The feature is listed and the card says why it is not on the map, because a feature missing from the map with no explanation is worse than one that is accounted for.

CaseWhat happens
A coordinate outside the range of the earthThat feature is not drawn. Every other one still is.
A ring that does not close, or has fewer than four pointsThat feature is not drawn. A polygon's rings must close, per RFC 7946.
A feature with "geometry": nullListed as having no geometry, and left out of the area the map frames.
A stated crs that is not CRS84Nothing is drawn, and the card says so. See below.
A malformed bboxNoted. The map is drawn from the coordinates, which is where it always comes from.

A document that names EPSG:4326 is not drawn.

RFC 7946 removed crs and fixed the coordinate system, so a conforming document does not carry one. A document that still does is only drawn when it names CRS84. EPSG:4326 is refused even though it describes the same datum, because many tools write that name with latitude first and nothing in the document says which order was meant. Drawing it would put every feature in the wrong place with no sign that anything was wrong.

What the card shows

A heading counting the features, then the geometry mix and anything not drawn. Then one row per feature:

ShownNotes
NameFrom properties.name, then title, then label, then the feature's id, and otherwise "Feature 1", "Feature 2" and so on.
GeometryThe type, verbatim.
PositionFor a lone point only. A polygon's corners are not positions anybody reported.
SizeRings and points, for anything that is not a lone point.
PropertiesEvery key and value the feature carries, as text.
NoteOnly when the feature is not drawn, saying why.

A long list scrolls inside the card rather than pushing the rest of the channel out of reach. The card does not carry the document itself: the raw text is the longest thing a document holds, and a card sits in the channel under everything else somebody wrote. Open details puts it in the sidebar under As posted, which is what you check the card against.

Documents that do not say they are GeoJSON

With EnableGeoJSONUnlabeled on, three further spellings are read: a fence labeled json, an attachment named .json, and a document pasted with no fence at all. The switch ships off.

It widens what is read, never what is accepted. Anything that does not parse as GeoJSON is still left alone, so a package manifest, a JSON Schema fragment and an API response are all untouched. A document you fenced as code is never read either, whatever the switch says. And only a block labeled geojson is told why it was refused: the ambiguous spellings fail silently, because a notice on each of them would fire constantly on ordinary posts.

How big it is

A line is given its length, an area its area, and a point neither. A collection gets both when its members provide both, since it is one feature. A feature that is not drawn is not measured: a figure printed beside "not drawn" would be claiming something this build has just declined to claim.

Three significant figures, deliberately.

The measurement models the earth as a sphere, which is within about half a percent everywhere; your coordinates are written to whatever resolution the source chose; and a route measured off a map is not a surveyed distance. Printing 12.4174 km would claim a precision none of those support, so the figure is cut to what it can carry. A polygon's holes are subtracted from the ring that encloses them.

The style a document states

GeoJSON itself says nothing about appearance, so styling travels in ordinary feature properties under the names simplestyle settled on. These are read:

PropertyApplies toExample
strokeLine, polygon outline"#ff0000"
stroke-widthLine, polygon outline3
stroke-opacityLine, polygon outline0.8
fillPolygon"#ff0000"
fill-opacityPolygon0.25
marker-colorPoint"#0000ff"
marker-sizePoint"small", "medium", "large"
 
"properties": {
  "stroke": "#ff0000",
  "stroke-width": 3,
  "stroke-opacity": 0.8,
  "fill": "#ff0000",
  "fill-opacity": 0.25
}

Each name is read for the geometry it belongs to. A point carrying both marker-color and fill is drawn in the one meant for a marker, and a point's fill-opacity is ignored rather than deciding how solid the marker is.

marker-symbol is listed, not drawn.

A symbol name points into an icon set. This plugin ships an offline basemap with no icon set in it, so there is nothing for a name to point at. The property is shown among the feature's properties like any other, so nothing is lost, but no icon is drawn for it.

What is refused, and what happens then

A color must be a hex triple, #f00 or #ff0000. A width must be a number above zero and no more than 10. An opacity must be a number from 0 to 1; zero is a real value and means invisible. A size must be one of the three words above.

Anything outside those is refused, not adjusted: the value is shown as text among the feature's properties and that part of the shape is drawn in the theme's own style. Clamping a width of 4000 down to 10 would draw something the document did not ask for while claiming to honor it, and a value handed to the map unchecked is a value the browser will interpret.

A polygon that states no fill-opacity is filled at the same low opacity every shape on these maps uses, so a colored area never hides the ground underneath it. A stated one replaces that rather than combining with it: 0.25 means a quarter.

What the sidebar shows

Open details on the card opens the sidebar on the document. It carries the same summary and feature list the card does, and it is where a point's position becomes a link into the coordinate tools.

Only a feature that is a single point is linked, and only when its coordinate carries enough digits for the coordinate grammar to stand behind. A polygon has no one position and a multi-point has several, so linking either would be picking one and calling it the feature's. A coarsely written coordinate, and a document posted by a build older than this one, both read as plain text rather than as a link that would land nowhere.

Choosing what the sidebar shows

Customize your view at the bottom of the panel hides sections you do not want. The choice is yours alone, it applies to the sidebar only, and the card in the channel and the stored message are both unchanged.

SectionWhat it holds
MapEvery feature drawn together, fitted to all of them.
What the document holdsHow many features, of what geometry, and anything not drawn.
FeaturesEach feature by name, with its geometry and size.
Feature propertiesThe keys and values each feature carries.
As postedThe document exactly as it was posted, scrollable. Collapsed until you open it, with a button that copies it.

These are separate from the Cursor on Target sections.

The two panels hold different things, so they keep separate lists. Hiding the map here leaves the Cursor on Target map alone, and the other way round. Hiding every section is allowed: the panel keeps its heading and the Customize link, which is how you get back.

The map

Every feature is drawn together and the map opens fitted to all of them, not to the first. A document that straddles the antimeridian is framed across the seam rather than around the far side of the planet, and a document of a single point opens at a readable span rather than at maximum zoom.

Points are drawn as markers, lines and areas as outlines with a light fill. There is no pin: a document of nothing but polygons reports no single position, and this build does not draw a position nobody stated.

The map is the same one the coordinate tools draw, over the same offline basemap, and it follows the same settings. Under a post it is drawn when EnableLocationMap and EnableLocationMapInline are on, and a reader who has turned the map under posts off in their own settings does not get one there either. In the sidebar it follows EnableLocationMapPanel and this panel's own Map section instead, so hiding the map under posts does not blank the one in the sidebar. There is deliberately no separate GeoJSON map switch.

Open larger

Under the map is Open larger, which opens the whole document in a new tab with the window given to one picture. It is the same map, drawn from the same post, and nothing else: close the tab to go back to the post it came from.

The address is the post, not a coordinate: a document of several features has no single position that names it. Opening it re-reads the post, so a reader who may not see the channel gets nothing found, and a post whose card has stood down has no page either. It follows EnableLocationMapPage, like every other map page.

What the card will not claim

  • It never invents a position. A feature with no usable coordinate is listed and not drawn.
  • It never re-rounds a coordinate. What you see is what the document wrote.
  • It never renders half a document. Anything over a limit is refused whole.
  • It never guesses a projection. A document whose axis order cannot be confirmed is not drawn at all.

A card is frozen at the moment it was posted.

The document is read once, as the post is created. Editing the post stands the card down and shows the text again, which is the supported way to change or remove one. A card posted by an older build keeps whatever that build understood.

Settings and troubleshooting

A card changes what the post is.

Rendering a document sets the post's type, and a typed post loses its Elasticsearch and OpenSearch matches, its auto-translation and its embeds. Its file attachments are unaffected and Mattermost still lists them under the card. EnableGeoJSON is how an install opts out. A post carrying a document is also never decorated, so a coordinate written beside one is not linked. Installs searching through Postgres are unaffected either way.

Turning either setting off leaves new posts alone; posts already rendered keep their card. If a document you posted did not render, see Troubleshooting.
