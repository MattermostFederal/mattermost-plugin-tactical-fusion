Troubleshooting

Symptoms, causes, and fixes. Codes link into the registry.

A time was not turned into a link

Working from most to least likely:

CauseHow to tellFix
The format is not one that is recognized Compare against the declined list. Epoch seconds, 12 hour clocks, bare dates and CST style abbreviations are all deliberately absent. Write it as a date-time group or an RFC 3339 timestamp.
It is inside a protected span It sits in a code fence, inline code, a link, or inline HTML. Working as intended. Move it into ordinary prose if you want it linked. See protected spans.
The format is switched off Run /tactical-fusion examples. It ends with a note when decoration is off, and shows each format's real result. Turn the format on in System Console, Plugins, Tactical Fusion.
The message was edited The time was added or changed in an edit rather than the original post. Working as intended. Edits are stored verbatim, on purpose, so the plugin never transforms text you deliberately authored.
The message predates the plugin It was posted before the plugin was installed or enabled. Working as intended. There is no backfill; only new posts pass through the hook.
The message would have been too long Server log carries TF-11001. Working as intended. Decorating would have pushed the post over the maximum size, so it was posted undecorated rather than rejected. Shorten the message or split it.
A decorator panicked Server log carries TF-11000. A genuine bug. The post was left unmodified, so nothing was lost. Report it with the log line.

A coordinate was not turned into a link

Run /tactical-fusion check <your text>. It runs the real matcher against exactly that text and reports what it did, without posting anything. That answers this question directly and is faster than working through the list below.

The usual causes, in the order they come up:

SymptomCauseFix
21.34, -157.95 did nothing, but 21.3353, -157.9483 works Signed decimal degrees needs at least four decimals on both values. Write the full precision, or add hemisphere letters: 21.34 N, 157.95 W is accepted.
A coordinate at the end of a sentence did nothing A full stop or comma directly against the last digit is indistinguishable from a range or a list at the point the check runs. Put a space before the punctuation, or accept it. This is a deliberate trade against rewriting the middle of -157.9483..-157.9583.
21N157W did nothing The shortest USMTF shape is only matched behind a field label. Write LATD:21N157W.
4qfj0906059620 did nothing, but 4QFJ0906059620 works A run-together grid reference has to be upper case. Lower-case hexadecimal of that shape is what a short git commit hash looks like, and about one in 3,900 of them is a valid grid reference. Write it in upper case, space it out, or write MGRS: in front.
4QFJ0959 did nothing, but 4QFJ090596 works A run-together reference needs at least three digits per axis, a 100 m square. Shorter runs are what part numbers look like: 26HMA1997 is a valid grid reference, and about one uppercase run in 75,000 collides at two digits. Space it as 4Q FJ 09 59, or write MGRS:4QFJ0959.
4Q6090602359620 did nothing, but 4Q 609060 2359620 works UTM run together has no letters to check: after the zone and band it is thirteen bare digits. Space it out, or write UTMO: in front.
XGKP5535 did nothing, but GEOREF:XGKP5535 works GEOREF is matched behind its label and never bare. Four letters and four digits has nothing in it that a part number does not. Write GEOREF: in front. EnableLocationMoniker also has to be on, or the label is not read either.
045KG14 did nothing, but GARS:045KG14 works GARS is label-only too, and it is the weaker of the two: seven alphanumerics whose only structural check is that a third of the letter pairs name no band. Write GARS: in front, and check EnableLocationMoniker is on.
73h483p2+4m did nothing, but 73H483P2+4M works A bare Plus Code has to be upper case. A lower-case run of that shape is what a version string with build metadata looks like, and roughly one in 50,000 of those is a well-formed code. Write it in upper case, which is how Plus Codes are normally written, or put PLUSCODE: or OLC: in front.
CWC8+R9 did nothing That is a short Plus Code. It only means anything relative to a nearby place, which this plugin has no way of knowing. Use the full code, 73H483P2+4M. Google Maps shows the full form beside the short one.
A UTM position did nothing, but MGRS and lat/lon work UTM is off by default, and is the only format that is. Its band letter is ambiguous, so a wrong reading is a confidently misplaced position rather than a missed decoration. An admin turns on EnableLocationUTM in the System Console. Read that section first: it explains when the default is the right one for your workspace.
A UTM position opened on a latitude nowhere near the one intended The letter after the zone is read as a latitude band, never as a hemisphere, so 11S is band S (34 north) and not "zone 11, southern hemisphere" (56 south). A southern-hemisphere position written that way is usually declined, because its northing does not land in the band, but not always. Write southern positions as a grid reference, or as latitude and longitude. Delete the link while editing the post to opt that one message out.
A grid reference with plausible-looking letters did nothing Only eight of the twenty-four 100 km column letters are legal in any given zone, and the row letters are staggered in even-numbered zones. 4QJJ123123 names no real square. Check the letters against the zone. check will confirm.
A polar coordinate has no MGRS or UTM row Above 84° north and below 80° south there is no UTM grid. That is Universal Polar Stereographic, a different system this plugin does not implement. Nothing to do, and less is missing than it looks. The coordinate is still decorated, still shows latitude and longitude, and still shows its GEOREF, GARS and Plus Code rows: those three subdivide the graticule rather than a projected grid, so they have no polar gap and are what remains at those latitudes.
One coordinate in a list linked and the others did not A coordinate directly adjacent to another number is read as part of a numeric list. Separate them with something other than a comma and a space, or put each on its own line.
Nothing in the message linked, including a coordinate you are sure of The format, or coordinate decoration as a whole, is switched off. Check the admin settings. check reflects them, so it will say nothing matched.

The panel shows fewer decimals than I typed

It shows what the original text carried, and no more. A coordinate written to two decimals is only good to about a kilometer, so rendering it back at six would invent precision that was never there.

If the panel is coarser than you expected, the coordinate in the message is coarser than you expected. The As written row shows exactly what was parsed.

An airfield code was not turned into a link

Run /tactical-fusion check <your text>. It runs the real matcher against exactly that text and reports what it did, without posting anything.

An airfield code is checked against the database, not against a shape.

Four letters vouch for nothing, so a code this build's database does not hold is left as plain text rather than linked to a panel that would then have nothing to show. That is unlike every other format here, where the text alone decides.

SymptomCauseFix
KIND on its own did nothing There is no bare grammar, permanently. Of the airfield codes this plugin ships, 343 are ordinary English words: FACT is Cape Town International, USCG is an airfield in Russia, LIMA is in Turin. Reading them bare would rewrite ordinary prose. Write a USMTF field label in front: ICAO:PHNL, LOC:, DEPLOC: or ARRLOC:.
icao:phnl did nothing, but ICAO:PHNL works The label and the code are both matched in upper case only. Coordinate labels accept any case because their tokens carry digits; four letters do not, and loc: fast turnaround on the ramp would link FAST. Write both in upper case, which is how USMTF writes them.
ICAO: PHNL did nothing, but ICAO:PHNL works Nothing may follow the colon. A space there would let the label reach the next word of an ordinary sentence, and this traffic is often written in capitals: LOC: FAST TURNAROUND ON THE RAMP would rewrite FAST into a link to an airfield in South Africa, permanently. Write the code directly against the colon, which is how a USMTF field is written. A space before the colon is still fine.
ICAO:QZQZ did nothing Those four letters are not in this build's airfield database. Check the code. If it is right and simply new, a later plugin build may hold it: the database ships with the plugin.
ICAO:PHN or ICAO:PHNLX did nothing An ICAO ident is exactly four letters. Three is an IATA code, which this plugin does not read. Write the four-letter ICAO ident. The IATA code is shown in the panel for a field that has one.
logs/ICAO:PHNL did nothing A slash on either side declines the match, so a label inside a path is not read as a field label. Rewriting the middle of a path is exactly what that guard exists to prevent. Nothing to do. A genuine set line ending DEPLOC:PHNL// does decorate: the trailing // is matched and left in the message.
The label was consumed and only the code is left Not a failure. The label is absorbed into the link, the same way DTG: and the coordinate labels are, because the link already says what it is. Nothing to do. The stored message keeps the code, never the airfield's name: that changes between builds and this hook rewrites what you wrote.
No airfield code in any message links Airfield decoration is switched off. Check the admin setting. There is one switch, not two: the grammar is label-only by construction, so a separate label switch would turn the whole thing off under a second name.

A Cursor on Target event was left as plain text

An event that cannot be rendered is never refused: the post goes out with the XML as ordinary text, which is exactly what you typed. When the event was in a block you labeled cot the plugin also sends you a message, visible only to you, saying which of the two happened.

Only a cot block gets that message. A block labeled xml, a bare event with no fence, and an attachment all fail silently, because plenty of XML is not Cursor on Target and a message on every one of those would fire constantly on ordinary posts. Labeling a block cot is how you say you meant it, and asking is what earns you the answer.

SymptomCauseFix
The Cursor on Target event you just posted could not be read, so it was left as ordinary text. The XML did not parse, or it parsed into something this plugin refuses: a document type declaration, a processing instruction other than the XML declaration, an event with no uid, type or time, more than 32 events, or text that is not valid UTF-8. Code TF-11005. Check the event against what is and is not rendered. The message text is unchanged, so nothing was lost.
The Cursor on Target event you just posted carries too much detail to render, so it was left as ordinary text. The event parsed, but the card's data would have been larger than the space a post has for it. A very long remarks, or a large block of events, is the usual reason. Code TF-11004. Shorten the remarks, or split the block across two posts. The whole event is still in the message.
An attached .cot or .xml file did nothing, and nothing said why Attachments fail silently, for the reason above. What reaches the server log depends on where it stopped: TF-11003 when the file could not be read at all; TF-11006 when it was read but is not yours, is already on another post, or has been deleted; TF-11005 when it was read but its contents did not parse; TF-11004 when it parsed but carried too much detail. A file whose name does not end .cot or .xml, and one over 64 KB, are passed over with nothing logged at all. Check the rules in as an attached file: exactly one file, under 64 KB, one you attached to this post. A file your integration uploaded through the plugin API also counts, since those are credited to the server rather than to a person. Pasting the same event into a cot fence gives you the reason directly, which is faster than asking an administrator to read the log.
The event renders for me but not for a colleague The card is drawn by the webapp. A client that has not loaded the plugin's bundle, or has an older one, falls back to the post's text. Mobile shows the text for the same reason. Reload. The text is always there underneath, so nobody sees nothing.

Editing the post removes the card for good.

The card is drawn from data captured when the post was made, and there is no hook that recaptures it on an edit. Once a post carrying an event has been edited, the event is shown as text from then on. This is deliberate: a card that kept claiming readings the edited message no longer contains would be worse than no card.

Nobody else sees the link, or only some clients do

The link is in the stored message, so every client sees the same text. What differs is what happens on clicking it: clients running the plugin's web bundle open the sidebar, and everything else follows the link to the server-rendered page. Both show the same instant.

Editing a post shows markdown instead of the time I typed

Working as intended, and the main cost of decorating on the server. The link is the stored text. Deleting the link syntax while editing is the supported way to opt one post out; the plugin will not put it back.

"That link is missing or has an invalid date-time group" or "invalid coordinate"

Code TF-17000 for a date-time group, TF-17001 for a coordinate. The query string carries no usable instant or no usable position. Almost always a hand-edited or truncated URL, or a link copied out of a message and reassembled by something that mangled the query string. Click the original link in the channel rather than a copy.

The map page refuses the same links under the same code, worded That is not a coordinate this plugin issued. Despite matching the wording of TF-13008 it is this failure, not that one: check the code rather than the sentence.

The airfield page refuses a link the same way under TF-17002, worded That is not an airfield code this plugin issued. A code that is well formed but absent from this build's database is a different thing and renders the page with a note instead; see the airfield messages.

The sidebar says "Not a coordinate"

Code TF-13008. The server was asked to convert the coordinate in that link and answered that it is not one this plugin issued. The panel refuses to render anything rather than showing a position that may name somewhere else entirely, which is the same thing the standalone page does for the same link.

Almost always a hand-edited or reassembled URL. If you see it on a link you clicked directly in a channel and did not edit, that is worth reporting with the code and the link.

This is distinct from the grid rows reading unavailable, which means the request did not arrive at all. That leaves the rest of the panel intact and usually clears on reopening.

Clicking a link asks me to sign in

Expected. The pages a decorated link opens outside the sidebar, both the readings page and the map page behind Open larger, require a Mattermost session. Without one you are sent to the sign-in page carrying the link you clicked, so signing in takes you on to the coordinate rather than dropping you at the home screen.

The usual cause is a session that expired while the tab sat open, or a link opened in a browser you are not signed in to. Nothing is lost either way. If you are asked on every click while Mattermost itself stays signed in, that is worth reporting: it points at cookies not reaching the plugin's own routes rather than at the link.

Clicking a coordinate opens a page instead of the sidebar

Clicking a decorator link is meant to open the right-hand sidebar without the browser navigating anywhere. Landing on a full page instead means the webapp did not recognize the link as one of its own and stood aside, letting the browser follow it.

Everything on that page is correct, so nothing is wrong with the coordinate, and it is easy to mistake for a deliberate choice. It is not. It usually means the server and the webapp bundle are from different builds, so reload the page first: a browser holding a cached bundle from before an upgrade is the common cause. If a reload does not fix it, report it with the link and the plugin version, since nothing is logged on either side.

The map is missing, or will not load

The map is drawn in your browser, so it can fail in ways the readings cannot. Every reading in the table renders regardless: the coordinate and its conversions are worked out on the server. The one thing that goes with the map is the country, which the map speaks and nothing else does.

Check the switch before anything below.

A map that is missing everywhere, with no message where it should be and no tick box for it under Customize your view, is not a failure: it is switched off for the workspace. Nothing is logged and nothing says so in the panel, because to a reader on such an install the plugin simply does not draw maps. The rows below are for a map that is trying to draw and cannot.

Two things about the map under an airfield.

The airfield panel draws the coordinate decorator's own map, so it follows the same panel-map switch, and that switch is combined with coordinate decoration itself: an install that turns coordinates off loses the airfield map too, even though airfield codes keep decorating.

The standalone airfield page draws no map at all, deliberately. It links to the coordinate page, which draws one. That is the one place the two airfield surfaces differ, and it follows from the page carrying no script.

What it saysCauseFix
This browser cannot draw the map. The browser has no WebGL2. Usual on a hardened or virtualised desktop where hardware acceleration is off or WebGL is disabled by policy, and in some remote-desktop sessions. Nothing you can do in the plugin. Enabling hardware acceleration, or WebGL, is a browser or desktop policy decision.
The map could not be loaded. The bundled basemap did not arrive, or what arrived was not a basemap. Either it is missing from the deployed bundle, or something between the browser and the plugin is not serving it correctly. See below.
Stuck on Loading map… Ordinary while the map library and the basemap arrive. The first coordinate of a session is the slowest, because it fetches the library. Wait, then reload. If it never clears, report it.
The position for this coordinate is unavailable. Nothing is wrong with the map. Either the conversion did not arrive for a grid reference, which has no latitude and longitude until the server works one out, or the position is a polar one outside the grid entirely. Rather than guess at a pin, the map says so. For a conversion that did not arrive, reopen the coordinate. Every reading the link carries by itself stays on screen either way. See when the conversion does not arrive.
This position is too far north for the map.
This position is too far south for the map.		 Expected, and not a failure. The projection the map uses runs out at about 85 degrees north and south, so a coordinate beyond that is left off rather than pinned up to 550 km from where it actually is. None. The coordinate is fine and every reading renders. See the map.

The map could not be loaded. is deliberately distinct from a blank or half-drawn map: rather than draw an empty sea, the plugin checks the basemap on arrival and says so when it is unusable. Two causes are worth checking in order.

  • The basemap is not in the bundle. Open /plugins/com.mattermost.plugin-tactical-fusion/public/map/world.pmtiles on your own server. A 404 means the plugin was built without it; rebuild and redeploy. This is the likelier cause on a plugin built from source.
  • The basemap is served, but not in pieces. The map reads the file in ranges rather than downloading it whole, so a proxy, a CDN or a storage backend that ignores HTTP range requests breaks it while making the file itself look perfectly healthy. If the URL above downloads a large file successfully but the map still refuses, this is the cause, and the fix is in front of Mattermost rather than in the plugin.

A momentary network failure is treated differently on purpose: it is not remembered, so simply opening another coordinate retries. A cause from the list above is remembered for the rest of the session, so that a broken deploy does not have every panel you open asking for the same file again.

A detail area will not install, or never appears

Above zoom 10 the map draws OpenStreetMap detail for the areas this install has, and each area is one file on disk. Two very different things send people here, and the fix has nothing in common between them.

No detail anywhere past zoom 10 is not a failure.

Detail is shipped per area rather than for the whole world. Outside a covered area the world map keeps drawing, magnified past the detail it holds, which is the expected behavior and is described under the map. This build ships Hawaii and Guam; anything else was added by whoever installed the plugin, through the package directory. The credit beneath the map does not answer this: it is drawn whenever this install's detail areas went into the map at all, so it appears at every zoom and everywhere in the world once any area is installed. What tells you an area is covered is the map itself, real road networks and named water where the world map carried none. See the map.

The rest of this section is for an area that was meant to be there. Either the System Console refused to install it, which says why on screen, or the file is in the directory and the area still never appears, which says nothing on screen at all and has to be read out of the server log.

A file is in the directory and the area never appears

This is the case with nothing on screen. A package that fails validation is dropped and logged rather than served, because a bad archive that reached a browser would draw nothing and say nothing, and the reader would see an area that is simply missing. The log line is the only thing that will ever explain it, and it names the file.

Each rejected file is logged once, not once per request.

Discovery is memoized, so a bad archive writes one line rather than one per map tile a reader pans past. Replacing a bad file with another bad one under the same name is therefore silent until the plugin restarts.

CodeIn the logCause and fix
TF-18001 ignoring a map package whose name is not <command>-<area> A .pmtiles file in the directory whose name is not an area name. Rename it.
TF-18002 ignoring a map package that is not the archive it claims to be The file failed validation. The reason travels with the line; see the table below.
TF-18000 cannot locate the plugin bundle, so no bundled map packages are served The plugin cannot find its own directory on disk, so the areas it ships are unavailable. Anything in the package directory is unaffected. Unusual, and worth reporting.
TF-12007 a discovered map package could not be opened An area was listed and then could not be read when a tile asked for it. Normal for the moment a file is being replaced by hand; persistent means the permissions changed under a running plugin.

The reason carried by TF-18002, TF-18006 and TF-18008 is one of these. The same four questions the browser asks on arrival are asked here, at discovery, so that the answer is one log line naming the file rather than an area that quietly does not draw.

The map is dark, but my Mattermost is light

Expected, and the same on all three surfaces: the sidebar, the hover card and both standalone pages. The map is drawn dark whichever theme you are using. Everything around it, the table, the note, the links and the page itself, still follows your theme, which is what makes the difference noticeable enough to look like a theme that failed to apply.

It is a deliberate choice rather than a defect. The dark palette carries the land and water edge better at the size a sidebar gives it, and it keeps the pin and the square around it from competing with the readings beside them. There is no setting for it, in the System Console or under Customize your view. If the map is unwanted in a light theme, hiding it is the only lever, and it is yours to pull per person.

The panel and the standalone page show different timezones

Expected if you have customized your view. The standalone page is rendered from the link alone and does not ask who is reading it, so it always shows the built-in defaults. It requires a login, but it does not consult your settings. There is no fix for this today.

Two timezone rows swapped places

Expected across a daylight saving boundary. Rows are ordered west to east by the offset measured at the date-time group's own instant, so two zones that observe daylight saving differently will genuinely change places between summer and winter. London and Reykjavik are the usual pair.

Messages when saving your view

A failed save stays open with the reason on screen, rather than closing and losing your edits. Every message below carries its code.

MessageCodeCause and fix
Not authorized. TF-13000 Your session expired. Reload Mattermost and sign in again.
Not ready. TF-13002 The plugin was still activating. Try again in a moment.
That is not a valid settings payload. TF-13005 The request body was not decodable or exceeded the size cap. Not reachable from the editor; it means something other than the sidebar sent the request.
Could not read your settings. TF-13004 The plugin key-value store could not be read. A server side problem; check the log for the matching line.
Could not save your settings. TF-13006 The store could not be written. As above.
Could not restore the defaults. TF-13007 The stored blob could not be deleted. As above.
at most N timezones may be selected TF-14005 Remove some rows. The count is taken after duplicates are collapsed.
the flash threshold must be between N and N minutes TF-14006 Choose a value in range. Clearing the field entirely means "use the default", which is always accepted.
"Local" is not a timezone identifier TF-14003 Pick a real zone. Local means whatever zone the server process runs in, which is not a place and can differ between nodes.
unknown timezone "..." TF-14004 Your browser offered a zone the server's timezone database does not have. Pick a neighboring zone and report the identifier.
"..." is not a timezone identifier TF-14002 Not reachable from the picker; it means something other than the sidebar sent the request.
a timezone label may be at most N characters TF-14000 As above.
a timezone label may not contain control characters TF-14001 As above.
"..." is not a row of the location panel TF-14008 The saved view named a row this version does not have. Not reachable from the editor, which offers one checkbox per row that exists. Note the asymmetry: writing an unknown row is refused, but reading one is not, so retiring a row can never lock you out of your own settings.

The plugin will not activate

Check the server log for TF-10000 or TF-10001. TF-10000 means two decorators claimed the same type, or one declared an empty type; TF-10001 means the slash command could not be registered, which usually means another plugin already claims the same trigger. Both are build or install problems rather than configuration ones, so report either with the version number.

Reporting something not listed here

Include, if you have them:

  • The TF-NNNN code, from the message or the server log
  • The exact text you typed, and what was stored
  • The output of /tactical-fusion examples, which shows the live behavior of your server
  • Which settings are on. There are eleven, and one of them, EnableLocationUTM, is off until an admin turns it on
